## 1. Implemented changes

### Matching (`app/services/lms/guided_practice_service.py`)

For each wrong answer the system checks Domain, Topic, Cognitive level and Difficulty, then serves an **approved original Target-PDF question**:

| Priority | Match |
|---|---|
| **P1** | Domain + Topic + Cognitive level + Difficulty |
| **P2** | Domain + Topic + Cognitive level |
| **P3** | Domain + Topic + Difficulty |
| **P4** | Domain + Topic |

Rules that are kept or added:

- **Only weak Subtopics. Never an unrelated topic.** The candidate pool is still restricted to the Subtopic first, so Domain + Topic always match.
- **Only `approved` and active bank items.** Nothing is ever generated by AI. A weak Subtopic with no approved question returns `no_verified_questions` with the message *"There are no verified practice questions for this subtopic yet. Your teacher has been notified."*
- **The current wrong answers drive matching.** For each Subtopic these are the latest Baseline/Follow-up attempt that scored it (it replaces the score) plus Guided Practice misses since then. A Monday Follow-up therefore refreshes the matching targets.
- **Each wrong answer takes its turn** (round-robin) and gets *its own* best available match.
- **Unseen first.** An unseen question always beats a repeat. Repeats, once the bank is exhausted, rotate across the weak Subtopics (least recently practised first) and stay inside the best-match tier.
- **A difficulty only counts when the paper printed one.** `questions.difficulty` silently defaults to `medium`, so a defaulted value is never treated as a match. This is `question_attributes.known_difficulty`.
- The existing weakness logic is unchanged: weakest Subtopic first, mastery policy `subtopic_v1`, and Guided Practice is evidence only.
- Every served attempt stores `match_priority`, `target_question_id` and `match_json`. The API returns `match` (priority, rule, target and served attributes, never the answer key). The student UI shows *"Chosen because you missed a similar question (Domain + Topic + Cognitive level + Difficulty) · Understanding · Intermediate"*.

### Storage and extraction

- `app/services/lms/question_attributes.py` (new) holds one shared normalizer for cognitive levels (Knowledge / Understanding / Application / Analysis/Reasoning) and difficulty labels (Basic/Intermediate/Advanced → easy/medium/hard). Unknown text maps to `None` and is never guessed.
- Baseline/Follow-up path (`hybrid_mcq_extractor` → `MCQQuestion` → `mcq_to_question_fields` → `question_bank_service.create_question`) now carries `cognitive_level` and `printed_difficulty`. As a fallback it parses the legacy `"Cognitive level: X"` text.
- Target bank import (`target_bank_service._store_question`) stores both fields. The admin item API exposes them for review.
- Retake variants (`diagnostic_variant_service`) inherit both fields from the original question, as they already did for topic and difficulty.

### Incorrect-answer tracking (`subtopic_mastery_service`)

`lms_incorrect_answers` is an insert-only snapshot written on Baseline/Follow-up submission and on Guided Practice answers. Each row records:

- Question ID, Domain ID and Subtopic ID
- Cognitive level and known difficulty
- the student's selected option and the correct option
- source (`diagnostic` / `quiz` / `guided_practice`), attempt ID and assessment ID

It is idempotent per student, source and question. Students assessed before this change are backfilled once, lazily, from existing evidence.

### Teacher analytics (`analytics_service.parameter_breakdowns`, `teacher-analytics.js`)

Under every Domain and every Subtopic the teacher now sees, for each cognitive level and each difficulty:

- correct and incorrect answers, and the percentage
- weak students: those whose latest paper at that level had a miss
- **Baseline → Follow-up for the same students**
- Guided Practice answers, counted separately and never mixed into assessment percentages

Rules for honest display:

- Levels with no data are omitted.
- Answers whose paper printed no level are counted as "Not printed".
- A level practised only in Guided Practice is labelled *"not on any Baseline/Follow-up paper"* instead of being shown as 0%.

Existing Domain and Subtopic analytics are unchanged.

## 10. Remaining issues

1. **Content and coverage (blocks production).** 78 bank questions are `needs_review` (stacked fractions, radical indices). Two weak Subtopics in this journey have **no approved question**: Laws of Logarithms (all 10 `needs_review`) and Conjugate of a Complex Number (the bank calls it "Complex Numbers", so an alias needs admin confirmation). Students see the "teacher has been notified" message, and teachers see the gap.
2. **P2 and P4 cannot be exercised with the current DIL papers.** Every question is "Intermediate". The logic is covered by automated tests only. It will become live once papers print more than one difficulty.
3. **Small P1 tiers repeat.** With the bank exhausted, a wrong answer whose only exact match is one bank question (Factor Theorem *Understanding*: only Q97) gets that question every few turns. This is by design (best match first), but more approved questions per cognitive level would improve variety.
4. **Teacher analytics label difficulty with the canonical bucket ("Medium")**, while the papers print "Intermediate". Grouping must be canonical; a display alias could be added.
5. **20 pre-existing test failures** (§11). They are not caused by this change, but they need triage.
6. **External:** Groq `qwen/qwen3.8-27b` returned 503 "over capacity" on 2 of 3 Baseline uploads. The app reported it correctly and nothing was saved half-way.
7. **Configuration:** on a fresh database the active LLM provider defaults to **OpenAI**. Learning Chat generation then fails ("OPENAI API key is not configured") until an admin selects Groq (done via `PUT /admin/settings/llm` in this run).
8. **Security (pre-existing, unchanged):** the admin password is hard-coded in `app/utils/admin_init.py`.
9. **Startup ordering risk (existing pattern):** if this migration's `ALTER TABLE` were to fail, ORM queries on `questions` would fail until it succeeds. On Postgres 17 and SQLite it succeeded on both a fresh and an existing database.
10. **`tests/*` is in `.gitignore`.** The new `tests/test_four_parameter_matching.py` must be force-added (`git add -f`) when this is committed, or it will not reach CI.
11. **No load or concurrency test on the production stack.** Gunicorn does not run on Windows, and the dev server is single-threaded. Matching adds about 3 indexed queries per `next` call.
